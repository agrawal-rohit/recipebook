## Thought

### Goal

Remove the inbuilt registry (`packages/registry`) and all surrounding logic. Replacement behaviour:
1. No inbuilt registry — a source must always be added explicitly by the user.
2. Every CLI command that needs a source validates **before** running that a valid source exists (or prompts the user to add one).
3. The `config` CLI command is renamed to `configure`.

This is a discovery map only — **no production code is changed** (voyager exploration).

---

### `packages/registry` structure & exports

`Files`

- `packages/registry/` — a **content** package, not a library. `private: true`, name `@cheetos/registry` (`packages/registry/package.json:2`).
- `packages/registry/scripts/build-registry.ts` — the only source file. Imports `buildRegistry` from `@cheetos/core` and compiles `registry/` source tree → `registry.json` + `r/` (build output, gitignored).
- `packages/registry/tsconfig.json` — trivial, includes `scripts/**/*.ts`, emits to `dist/`.
- `packages/registry/registry.json` — the **only committed** artifact (~41KB lean index: `conditions`, `types`, `items`, `scriptIntegrity`, `itemIntegrity`). **Five test/exploration files exist elsewhere.**
- `packages/registry/dist/scripts/build-registry.{js,.d.ts}` — compiled `scripts/build-registry.ts`.
- Dependencies: `@cheetos/core` (workspace), `spdx-license-list`. No consumers — **nothing in the monorepo imports `@cheetos/registry` as a module.** It is a build-content package consumed only via its compiled `registry.json` + `r/` being copied into the CLI tarball at `prepack`.

### CLI structure & command routing

`Files`

- `packages/cli/bin/cli.mjs` — entry. Imports `dist/index.js`, catches errors, `process.exitCode = 1`.
- `packages/cli/src/index.ts:run()` — builds `cac("cheetos")`, declares `--registry <source>` option, defines `loadRegistry()` closure, calls `registerCommandsCli(app, loadRegistry)`, then `app.parse(...)` + `app.runMatchedCommand()`.
- `packages/cli/src/commands/index.ts:registerCommandsCli(app, loadRegistry)` — the single command registry. Registers exactly two CAC commands: `add [item]` and `config <action> [source]`. **There is no `list` command in `src`** (a stale `dist/commands/list.js` exists — dead compiled artifact).
- Commands: `commands/add.ts` (`addCommand`), `commands/config.ts` (`configGetCommand`/`configSetCommand`/`configUnsetCommand`), `cli/config.ts` (config read/write primitives: `configPath`, `readConfig`, `writeConfig`, `unsetRegistryConfig`, `CheetosConfig`).
- Dispatch flow: CAC action → `runCliCommand(action)` (`cli/errors.ts`) which awaits the body and maps `OperationCanceledError`/`InterruptError`/generic errors to `process.exit` — wraps each command body.

### Which commands use the registry & where pre-run validation could live

`Files`

- `add` — the only command that actually **loads registry data**. `commands/index.ts:38` calls `loadRegistry()` → `addCommand(registry, indexLocation, {items, overwrite})` (`commands/add.ts` @import `../utils/registry`). It needs a source to run.
- `config set/get/unset` — **do not** load a registry; they manage the saved source itself (`commands/index.ts:94` — `config` path never invokes the loader; verified by `commands/index.test.ts` which passes a loader that throws and asserts `config` never triggers it).
- `utils/registry.ts` — loaders: `locateRegistry`, `loadRuntimeRegistry`, `loadCompiledItems`, `bundledRegistryPath`. **The `bundled` fallback is exactly the inbuilt-registry behaviour to remove.** `locateRegistry` order: CLI `--registry` flag > `env.CHEETOS_REGISTRY` > saved config > cwd/fallback/bundled `registry.json`. Removing the inbuilt registry collapses this to: flag > saved config (or explicit file), and the "fallback/bundled" tail and error message must change.
- **Validation hook location:** `runCliCommand` (`cli/errors.ts:57`) is the natural single choke point that wraps every command body — a pre-run "assert a source exists, else prompt to add one" could be inserted there, or in `loadRegistry()` inside `index.ts` before dispatch, or per-command in `commands/index.ts` action bodies. `loadRegistry()` in `index.ts` is the current shared pre-load step for `add`.

### How sources are added/configured; where `config` is defined

- Explicit vs inbuilt: users configure via **explicit** `cheetos config set <URL|path>` (validates HTTPS policy / existing regular file → writes `~/.config/cheetos/config.json`), an env var `CHEETOS_REGISTRY`, or the `--registry` flag. The **inbuilt** default is the bundled `registry.json` copied at `prepack` (`bundledRegistryPath` → `path.resolve(__dirname,"../../","registry.json")`).
- `config` command defined: `commands/index.ts` (registration + `runConfigAction` + `parseConfigAction` + `ConfigAction` enum) → dispatch to `commands/config.ts` (the three `*Command` exports). `cli/config.ts` holds the persistence primitives.

## Plan

### Goal and constraints

Remove the inbuilt registry (`packages/registry`) and **all** surrounding logic. Going forward a source is **always explicit**: `--registry` flag, `CHEETOS_REGISTRY` env, or `cheetos configure set`. Before any command that needs a source runs, a valid source must exist — or the user is prompted to add one interactively. The `config` command is renamed to `configure` (clean break, no alias). Dead code is removed, including `buildRegistry` in core (orchestrator decision: delete — zero in-repo consumers after this change, zero tests, only consumer of the `esbuild` runtime dep; git history preserves it). Constraints: no production code is changed by this plan (sisyphus implements); the existing contract artefact `config-command-test-suite.mdx` must be updated by oracle, not contradicted.

### Alternatives considered

<Card title="Pre-run validation choke point">
  - **A. `runCliCommand` in `cli/errors.ts` (single choke point)** — rejected: it wraps *every* command, including `configure`, which must run without a source (chicken-and-egg: `configure set` is how you add one). Would need a per-command flag, adding indirection for no gain.
  - **B. Global pre-dispatch in `run()` after `app.parse()`** — rejected: inspecting `app.matchedCommand.name` before `runMatchedCommand()` is brittle CAC coupling and duplicates command knowledge in `index.ts`.
  - **C. (Recommended) In the `add` action in `commands/index.ts`** — `loadRegistry()` already runs first, before `animatedIntro`/`addCommand` do any work, so "validation before the command runs" holds with zero new plumbing points. `configure` never loads a source and is naturally exempt.
</Card>

<Card title="Prompt vs fail-fast">
  - **Fail-fast only** (simplest, AGENTS.md-aligned) — rejected: the user explicitly requested "or the user is prompted to add one".
  - **Always prompt** — rejected: hangs CI/scripts.
  - **(Recommended) TTY-gated prompt, fail-fast otherwise** — precedent exists (`animated-intro.ts:163` checks `stdout.isTTY`). Interactive: reuse `configSetCommand()` with no argument — it already prompts via `textInput`, validates HTTPS/file policy, persists, and prints. Non-interactive (`!process.stdin.isTTY`): throw the actionable error and exit 1.
</Card>

<Card title="Implicit cwd `registry.json` discovery">
  - **Keep probing the working directory for `registry.json`** — rejected: it is implicit discovery, contradicting "a source must ALWAYS be added explicitly".
  - **(Recommended) Explicit sources only** — flag > env > saved config; nothing else. Delete the cwd/fallback/bundled candidate loop entirely.
</Card>

<Card title="Fate of `buildRegistry` in core">
  - **Keep as public authoring API** — rejected by orchestrator: 890 untested lines plus the `esbuild` runtime dependency in a published package, with no in-repo consumer once `packages/registry` is gone.
  - **(Recommended) Delete** `core/src/build.ts`, its `index.ts` export, the `esbuild` dependency, and build-only helpers. Ceiling note: registry authoring is out of scope going forward; sources are authored and hosted externally.
</Card>

<Card title="`configure` rename mechanics">
  - **Keep a `config` alias** — rejected: clean break per request; no compat surface.
  - **(Recommended) Full rename of user-facing surface**: command name, usage string, action errors. Internal command-body exports (`configGetCommand`/`configSetCommand`/`configUnsetCommand`) keep their names — they describe the config-file domain, not the command name, and minimal diff wins.
</Card>

### Risks and verification

<Callout type="warn" title="Risks">
  - **Docs churn**: README/CONTRIBUTING lean on the default registry; the rewrite is the largest textual diff — keep it factual and minimal.
  - **Lockfile/workspace**: removing `@cheetos/registry` and `esbuild` requires `pnpm install`; typecheck catches stale project references.
  - **Prompt retry**: retry is capped at one; a persisted-but-broken source surfaces as a normal load error on the retry, not a prompt loop.
  - **Published `configure get` output change** (no default URL): user-visible behavior change — intended, and covered by the contract update.
  - **Stale `dist/` in published tarballs**: `prepack` still runs `build`; shrinking `files` plus a clean rebuild covers it.
</Callout>

### Behaviour contract

<Accordions>
	<Accordion title="locateRegistry — explicit sources only">
		- `locateRegistry#no-source-throws`: with no `--registry` flag, no `CHEETOS_REGISTRY`, and no saved config → throws `NoRegistrySourceError` (identified by `name`, not instanceof, until the class exists) whose message names `cheetos configure set`, `CHEETOS_REGISTRY`, and `--registry` — actionable remediation replaces the old `Registry not found (registry.json). Run \`pnpm run build:registry\`` hint.
		- `locateRegistry#explicit-only`: a `registry.json` in the working directory is **not** discovered; resolution is exactly flag > env > saved config, with no cwd/fallback/bundled candidate probing.
		- `locateRegistry#env-empty-shadows-saved`: an empty `CHEETOS_REGISTRY` shadows the saved config (kept `??` semantics) → `NoRegistrySourceError`.
		- `bundledRegistryPath` is no longer exported from `utils/registry.ts`.
	</Accordion>
	<Accordion title="add — pre-run source validation (prompt or fail fast)">
		- `add#prompt-when-no-source-tty`: on a TTY, a `NoRegistrySourceError` from the loader triggers the existing `configure set` prompt path (`configSetCommand()` with no argument → `textInput` → validate → persist), then retries `loadRegistry()` exactly once; the retried registry feeds `addCommand(registry, indexLocation, …)`.
		- `add#fail-fast-non-tty`: on a non-TTY stream, the same error exits 1 with the printed remediation and **no prompt** — an interactive prompt would hang CI. (Guard: already true pre-refactor, since the current code never prompts.)
		- `add#prompt-cancel`: canceling the prompt (`OperationCanceledError`) → exit 0, no load retry, no `addCommand` call.
		- `add#prompt-retry-once`: when the source added at the prompt still fails to load → the error surfaces, exit 1, and the prompt is shown only once (retry capped at one).
		- TTY is observed via `process.stdin.isTTY` (stubbed with a configurable property; restored after each test).
	</Accordion>
	<Accordion title="configure — rename and unset-state output">
		- `configure#wiring-get|set|set-prompts|unset`: dispatch under the command name `configure` with no `config` alias; `set` without a source still passes `undefined` so the command prompts itself.
		- `configure#wiring-source-rejection`: `configure get <source>` / `configure unset <source>` → `configure <action> does not take a registry source.`, exit 1, no dispatch.

## Docs

No bundled registry ships with cheetos anymore. A registry source is **always explicit**, resolved in this order:

<TypeTable
	type={{
		'--registry <source>': { description: 'CLI flag — wins over everything else.' },
		'CHEETOS_REGISTRY': { description: 'Environment variable; an empty value shadows the saved config (fails with no-source).' },
		'cheetos configure set': { description: 'Persisted to `~/.config/cheetos/config.json`.' },
	}}
/>

Adding a source:

```bash
# Persist a source (HTTPS URL or an existing local file path)
cheetos configure set https://registry.example.com/registry.json
cheetos configure set ~/registries/registry.json

# Or pass it per-invocation / via env
cheetos add --registry https://registry.example.com/registry.json
CHEETOS_REGISTRY=~/registries/registry.json cheetos add

# Inspect / remove
cheetos configure get    # -> registry:    (not set) + hint when nothing saved
cheetos configure unset
```

**First run of `add` with no source:** on a TTY, cheetos prompts you to add a source right there (same validation as `configure set`), then retries loading the registry once — cancel exits; if the added source still fails to load, the error surfaces and the prompt is not shown again. In a non-TTY (CI/scripts), it fails fast with exit 1:

```text
No registry source configured. Add one with `cheetos configure set <https URL or file path>`, set CHEETOS_REGISTRY, or pass --registry <source>.
```

A `registry.json` in the working directory is **not** discovered — implicit lookup is gone.

<Callout type="warn" title="Migrating from the bundled registry">
	Setups that relied on the bundled registry must add a source once:
	`cheetos configure set <https URL or file path>` (or set `CHEETOS_REGISTRY`, or pass `--registry`). The `config` command was renamed to `configure` with no alias — update scripts.
</Callout>
